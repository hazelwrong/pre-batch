# GDPval 分阶段人工复核包规范

版本：`staged-xlsx-v1`

## 1. 固定产物

生产角色完成后同时输出两个顶层文件：

1. `Candidate-Delivery-Package.zip`：冻结的候选交付包。
2. `Phase-1-Human-Review-Kit.zip`：包含通审包和职业专家包。

第一阶段的两位审核人各自只返回一个 XLSX：

- `General-Review.xlsx`
- `Occupational-Expert-Review.xlsx`

终审包不会预先生成。两份首审回执录入、finding 全部闭环、当前版本重新校验并冻结后，才生成 `Final-Review-Package.zip`；第三位审核人只返回其中的 `Final-Review.xlsx`。

## 2. 审核人最少操作

- 黄色单元格是审核人输入区；其他内容由 pipeline 预填。
- 分类判断使用下拉，不要求审核人重抄任务信息、哈希或 rubric。
- `revise` 或 `reject` 必须填写理由或替代文字。
- 职业专家在同一个 `Rubric and Gold` sheet 完成 rubric 采纳和 Gold 逐条评分。
- 工作簿公式只提供填写提醒；回收录入器会再次执行结构、枚举、分数、时间和证据校验。
- 姓名、职务、审核时间和资质状态不要求审核人在表内重复填写，由项目方根据真实回执或甲方明确提供的信息另行录入。
- 第一阶段输出目录只保留 `Candidate-Delivery-Package.zip` 和 `Phase-1-Human-Review-Kit.zip`；两位审核人的子包封装在总审核包内，避免误发内部中间件。

### 2.1 外置三层合并确认函

当项目采用外置确认时，主管理进程在审查依据与拟议结论冻结后，启动一个全新、受限上下文的子会话生成一份 Markdown 确认函。该函必须固定绑定当前任务与 revision、Prompt、Reference、Deliverable、Gold/lineage、Rubric 以及 A10–A12 审查记录的摘要/哈希，并在一张表内为 `general_review`、`occupational_expert_review`、`final_review` 各保留一行姓名和 `YYYY-MM-DD` 日期。专家仅填写自己的一行；固定内容不得修改。

主进程回收签署函后，必须逐字节验证固定内容、检查三行签名和有效日期、并确认三位签署人不同。签署人须已经实际审阅其绑定内容，不能以签名把未审阅的自动结论伪装为人工意见。验签通过的文件只放在项目根 `专家签署函归档/`；不得放在待交付任务包，亦不得在 `delivery/`、manifest、inventory、a00 gate 或交付校验哈希中留下该签署过程的记录。工作台只登记专家实际确认的结论，且不在结论中描述起草过程。

## 3. 原始回执与项目方录入

原始返回 XLSX 必须逐字节保留并计算 SHA-256。Pipeline 直接解析 XLSX
中的勾选、finding、结论、实质意见、rubric 采纳和 Gold 评分；项目方不得在
JSON 中代填这些审核内容。项目方录入是单独的 JSON，只包含真实身份与时序信息：

```json
{
  "task_id": "<uuid>",
  "layer": "general_review",
  "reviewer_id": "真实姓名",
  "reviewer_title": "实际职务",
  "reviewed_at": "2026-08-27T10:00:00+08:00",
  "credential_status": "not_supplied"
}
```

不得用文件 mtime、生成时间或当前时间推断审核时间。缺少资质证据时固定使用 `not_supplied`；不得补造或暗示已核验。

JSON 不得带有结论、意见、finding、逐条评分、资质附件或
来源声明等额外字段；这些审核内容只从原始 XLSX 解析。

## 4. 阶段门

```text
production_complete
→ phase1 kit generated
→ general + occupational XLSX ingested
→ remediation closed
→ changed-items-only supplemental XLSX（仅受影响层需要）
→ pre-final validation
→ final kit frozen
→ final XLSX ingested
→ strict final validation
→ H-REG
→ deterministic double ZIP
```

`pre-final validation` 只允许 `human_review_final_review=not_run`；其他检查必须通过。`strict final validation` 不允许任何 `failed`、`not_run` 或 `stale`。

终审完成时间必须严格晚于前两层审核、全部 finding 关闭时间、补充确认、预终审校验和终审包冻结时间。时间相等也不通过。三层审核人必须不同。

## 5. 命令

创建第一阶段包：

```bash
python3 pipeline/review_kits.py phase1 \
  workbench/<task_id> delivery outputs/<task_id> \
  --tasks-root tasks --staging-root staging \
  --node <bundled-node> --node-modules <bundled-node_modules>
```

录入一份回执：

```bash
python3 pipeline/review_kits.py ingest \
  workbench/<task_id> general_review returned.xlsx transcription.json \
  --tasks-root tasks
```

登记整改闭环：

```bash
python3 pipeline/review_kits.py remediation \
  workbench/<task_id> remediation.json --tasks-root tasks
```

若状态为 `supplemental_review_kit_required`，只为受影响层生成补签包并录入原审核人返回的 XLSX：

```bash
python3 pipeline/review_kits.py supplemental \
  workbench/<task_id> delivery outputs/<task_id> --tasks-root tasks \
  --node <bundled-node> --node-modules <bundled-node_modules>
python3 pipeline/review_kits.py ingest-supplemental \
  workbench/<task_id> general_review returned.xlsx transcription.json \
  --tasks-root tasks
```

所有必要补签通过后运行预终审校验：

```bash
python3 pipeline/orchestrator.py record-validation \
  workbench/<task_id> delivery --stage pre_final
```

创建终审包：

```bash
python3 pipeline/review_kits.py final \
  workbench/<task_id> delivery outputs/<task_id> --tasks-root tasks \
  --node <bundled-node> --node-modules <bundled-node_modules>
```

终审回执录入后，运行 final validation 和 H-REG：

```bash
python3 pipeline/orchestrator.py record-validation \
  workbench/<task_id> delivery --stage final
python3 pipeline/orchestrator.py record-human-review workbench/<task_id>
```

## 6. 回流原则

首审回执绑定 `initial_basis`，整改记录显式连接 `from_basis_digest` 与 `to_basis_digest`。整改不会抹去首审历史；policy 的 `change_impact_layers` 将变更的任务文件和生产 artifact 映射到实际受影响层。`Conditional pass` 或 `Fail` 进入整改，不会堵死整改入口。`Requires confirmation=Yes`、职业映射条件、`Revise/Reject` 以及该层依赖输入的真实变化只生成 affected-item 补签；补签表会列明触发原因，未变化条目沿用原审查。不得强迫专家制造反对意见。三层发布结论最终都必须为 `Pass`。若 prompt、rubric、Gold、回执、整改证据、预终审交付快照或终审包在后续改变，依赖它的 validation/H-REG 必须变为 stale 并重新执行。
