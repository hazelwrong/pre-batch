## 第 0 步:一份真实交付物 —— 这条不满足,后面全部作废

甲方口径:**deliverable 必须是真实工作场景里真实交付过的东西**——一份台账、一份实验报告、一份数据分析报告、一份评审备忘录。不是"看起来像真的"。

按这个顺序找,**找到哪档算哪档**:

| 档 | 内容 | 能不能用 |
|---|---|---|
| 最优 | 成套:真实输入 + 由它产出的真实交付物 | ✅ 优先花时间找这个 |
| 次优 | 真实交付物拿到了,配套输入拿不到 → 用真实输出**倒推**合成输入 | ✅ 合成的是 reference,deliverable 保持真实 |
| 不可接受 | deliverable 本身是生成的 | ❌ reference 再真也不成立 |

管道里有硬守卫:`provenance.json` 里交付物的 `source_type` 不在允许集合,直接拒收。

**你要交给我的**:
1. 交付物文件本身(xlsx / docx / pptx,业务上本来是什么格式就是什么格式)
2. 如果有,配套的原始输入材料
3. 这份东西是谁做的、什么场景、什么时候、有没有权限给这个项目用

## A. 开工前(agent 要用的输入)

| 项 | 是什么 | 怎么给 |
|---|---|---|
| **material_pool** | 上面那份真实交付物 + 配套记录 | 一个目录 |
| **source_manifest** | 这批材料的来源与许可登记 | 见下面 `source_inventory.json` |
| **occupation_standard** | **职业标准卡**:这一行的人日常交付什么、用什么口径和单位、看哪些指标、什么算做得好、外行会犯什么错 | 一份 md,1–2 页。可以我起草、你这行的人确认 |
| **coverage** | 这一批要覆盖哪些职业、配额多少 | 试跑一条的话,一句话说明即可 |

`references`(Agent 可见输入)不用你准备——由 agent 设计规格、脚本生成。

### A.1 真实材料调研结束后：每个任务补三位专家画像

每找到一条真实业务场景及其真实 deliverable/reference 材料，必须为**该任务单独**准备三位专家画像，分别对应：通用审查、职业专家审查、最终审查。三位专家不能跨层复用；一批多任务时编号和化名也不要重复。

每位专家必须提供以下字段：

```
expert_id       编号
alias           化名
expert_role     专家角色
expert_profile  专家画像：典型岗位、经验和审查视角
strengths       擅长点
first_thought   他看到材料后首先会想什么
```

每个 intake 根目录保存一份 `expert_profiles.json`，固定三条。画像用于理解专家思路、规划 reviewer 招募和预演实质反对意见，**不是资质证明**。`alias` 不能直接写入正式 `reviewers.json`；正式复核仍必须替换成真实、可核验且实际签署意见的人。

`alias` 统一使用 2–4 个汉字的自然中文姓名。优先常见姓氏和日常名字，避免英文名、拼音名、岗位词、编号、生僻字叠加，以及过度文艺或明显像 AI 生成的命名。这条只约束规划化名；真人复核的法定/实际署名不得翻译或擅自改成中文名。

专家画像应在真实材料调研结束后完成，但不能作为 gold、reference 或 prompt 的业务证据，也不要注册成 T10–T15 的 Agent 可见输入。

## B. 四份声明(可以我起草,你确认签字)

### `coverage.json`

| 字段 | 说明 |
|---|---|
| `task_family` | 任务族名,如 `vendor-selection-tco-and-weighted-scoring` |
| `workflow` | 工作流类型,如"多步跨文件分析与决策支持" |
| `duplicate_group_id` | 去重分组。**同模板、同种子、同解法的任务用同一个 id** |
| `template_family` | 模板族 |
| `expected_expert_hours` | 这一行的人从零做出来要多久,如 `6~9`。**是任务难度,不是我们花了多少工** |

行业、职业、输入输出格式、发布态由脚本自己算,不用填。

### `provenance.json`

**据实登记,不要为了好看把重构过程隐去。** 甲方问过一次"这些文件是真实还是生成的",据实登记反而是通过项;写成全真、事后被查出来是致命项。

```
source_record_prefix            来源记录前缀,以 # 结尾
defaults.rights_holder          权利主体
defaults.license                许可依据
defaults.deidentification_note  脱敏做了什么
defaults.acquisition_date       获取日期
defaults.contains_pii           是否含个人信息(应为 false)
roles.reference    {source_type, production_method, drafted_by}
roles.deliverable  {source_type, production_method, drafted_by,
                    revised_and_adopted_by}
roles.index / roles.validation_evidence  同上三项
```

`production_method` 要写实话,例如:`supplier work record; de-identified and reconstructed by <模型> into Markdown or XLSX`。

### `source_inventory.json`

候选材料清单,一条一份(组)材料:

```
source_id / source_type / description / adopted / rejection_reason / license
```

**未采用的也要登记,并写明未采用原因。**

### `gold_revision.json`

交付文件是从什么重构来的:

```
revision_record.source_material    原始材料是什么
revision_record.business_context   什么业务场景
revision_record.deidentification   脱敏了哪些
revision_record.scope              重构到什么程度(格式?结构?业务关系保留了吗)
```

## C. agent 跑完之后:评分与复核(**必须真人**)

### `gold_marking.json` —— 人工评分

rubric 里大约 40% 的条目机器判不了,必须人评。**不评就不能说 gold 达阈值。**

| 字段 | 说明 |
|---|---|
| `rubric_version` / `marked_by` / `marked_on` | 版本、评分人、日期 |
| `method` | 怎么评的 |
| `independence` | 据实声明是自评,**不作独立性主张** |
| `items[]` | 每条:`code`、`score`、`awarded`、**`evidence`(取证位置)**、`shortfall`(未达成时写缺什么) |

两条硬纪律:
- **每条都要标注取证位置**。没有定位理由的分数不是评分,是断言。
- **gold 不应满分**。至少要有条目被判未达成并写明缺什么——满分说明评分标准是照着 gold 裁的。这是加分项不是减分项。

### `reviewers.json` —— 三层人工复核

**必须三个不同的人**:通用审查 / 职业专家审查 / 终审。

每层:`reviewer`、`title`、`date`、`findings`(实质意见,不是"通过")

职业专家还要:

| 字段 | 说明 |
|---|---|
| `rubric_version_reviewed` | 复核的是哪个版本。**版本不匹配不予采信** |
| `items_reviewed` | 实际逐条看过的条目 |
| `adoption_rounds[]` | 每轮:`round`、`date`、`rubric_version`、`adopted`、**`objected`**、`objection` |
| `credential_status` | 资质核验状态；未提供附件时必须写 `not_supplied` |
| `credential_evidence` | 可选；未提供时保持空，不构成阻塞但不得暗示已核验 |
| `remediated` / `remediation` | 提的条件怎么闭环的 |

**专家必须有驳回记录。全票通过的复核记录本身就是可疑信号**,管道里这是一道会转红的检查。

## 顺序

```
你:找到真实交付物 + 来源许可 + 职业标准卡
         ↓
agent:蓝图 → 参考文件规格 → prompt → 冷解题 → 冷复算 → rubric
         ↓
你:gold 人工评分 + 三层复核签字
         ↓
脚本:组装 → 全检 → 打包
```

前两份声明(`coverage.json` / `provenance.json`)在 agent 跑之前或之后填都行,但**必须在打包前齐**。

## 试跑一条,最少需要你给什么

1. **一份真实交付物**(最好带配套输入)
2. **它的来源、权利和脱敏情况**——三五句话即可,我来落成 `provenance.json` 和 `gold_revision.json`
3. **这个职业的一份标准卡**——或者告诉我职业和场景,我起草你确认
4. **三位复核人**——通用审查、这一行的从业者、终审,三个不同的人
5. 专家评分那一步的**时间**:大约 1–2 小时逐条看 gold 并写取证位置
